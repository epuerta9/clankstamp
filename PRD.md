# PRD: **clankstamp**

> **Naming note:** This PRD was originally drafted under the working name **openReplay**.
> The shipping name is **clankstamp**, and the durable artifact is a **stamp**
> (one stamp = one replay-able tour of one agent-produced change). When this
> document says *openReplay* think *clankstamp*; when it says *replay artifact*
> think *stamp*. The CLI binary is `clankstamp`. The project-local store is
> `.clankstamp/`. Otherwise the PRD below is unchanged.

---

## 1. Product summary

**openReplay** is a Go-based CLI, artifact format, and nvim cockpit for creating human-readable replay tours of AI coding work.

The core idea:

> Diffs show **what changed**.
> Chat shows **why the agent said it changed it**.
> openReplay combines both into a guided replay so the human can quickly rebuild their mental model.

The first product is a single Go binary called:

```bash
openreplay
```

It ships:

1. A CLI for creating, validating, indexing, and viewing replay artifacts.
2. An embedded nvim Lua plugin installable from the binary.
3. An embedded agent skill installable globally or per-project.
4. A standard `.openreplay/` JSONL-based artifact format.
5. A replay tour UX where the developer can hit **next** until they understand the change.

---

## 2. Problem

AI coding agents can now produce large, coherent changes quickly, but humans lose visibility.

The current review modes are inadequate:

| Surface             | Strength             | Weakness                             |
| ------------------- | -------------------- | ------------------------------------ |
| Git diff            | Precise code delta   | Too low-level and file-ordered       |
| Chat transcript     | Captures explanation | Detached from exact hunks            |
| PR summary          | High-level overview  | Often too compressed and post-hoc    |
| Agent plan          | Intent before work   | Does not prove actual implementation |
| Manual code reading | High confidence      | Mentally expensive                   |

The human has to reconstruct:

```text
plan → agent reasoning → files touched → code hunks → behavior change → tests → risk
```

That reconstruction is currently manual.

---

## 3. Product thesis

AI coding needs a standard **human-to-agent replay mechanism**.

An agent should not just leave behind a patch.

It should leave behind a guided, durable explanation trail:

```text
what changed
why it changed
where it changed
how it maps to the plan
what evidence supports it
what the human should review
```

openReplay creates that artifact and makes it navigable from nvim.

---

## 4. Goals

## Primary goals

1. **Create a portable replay artifact** for AI-generated code changes.
2. **Let humans replay an agent's work step-by-step** inside nvim.
3. **Support any agent harness**, not just Pi, Claude Code, OpenCode, or Codex.
4. **Ship as one Go binary** that includes the CLI, nvim plugin installer, and agent skill installer.
5. **Use JSONL as the event/source format** so replays can be streamed, appended, diffed, and generated by many tools.
6. **Support global and current-directory install** for agent skills.
7. **Support Claude Code skill format and open standard `SKILL.md` format.**

---

## 5. Non-goals

For v1, openReplay is **not**:

* A full IDE.
* A replacement for git.
* A replacement for PR review.
* A full agent harness.
* A chat app.
* A task manager.
* A Slate replacement.
* A general knowledge base.
* A system for exposing hidden model chain-of-thought.

The replay should store **rationale and evidence**, not raw/private chain-of-thought.

# 6. Core user experience

## Main nvim flow

User runs an agent.

Agent creates a replay artifact.

Then in nvim:

```vim
<leader>rr
```

opens replay picker:

```text
openReplay

1. BD-42 Add tenant-scoped API keys        ready      8 steps
2. Refactor invoice lifecycle              draft     11 steps
3. Fix webhook idempotency                 accepted   5 steps
```

Select a replay.

Then the tour begins:

```text
Step 1 / 8

New tenant API key model

What changed:
  Added a TenantApiKey model and migration.

Why:
  Machine clients need tenant-scoped authentication without user JWTs.

Files:
  app/models/tenant_api_key.py
  migrations/0042_tenant_api_keys.py

Review:
  - Are keys stored hashed?
  - Can keys be revoked?

Keys:
  n next
  p previous
  o open file
  d diff
  r mark understood
  a ask about step
```

When the user presses `n`, nvim opens the next relevant file/hunk and highlights it.

The user keeps pressing next until they are caught up.

# 7. Product primitives

## 7.1 Replay

A **Replay** is the durable artifact for one agent-produced change.

It contains:

```text
metadata
base/head git information
event log
tour steps
patches/hunks
test evidence
review state
```

## 7.2 Event

An **Event** is an append-only JSONL record.

Examples:

```json
{"type":"run.started","ts":"2026-04-27T08:12:01Z","run_id":"run_abc","title":"Add tenant API keys"}
{"type":"file.read","ts":"2026-04-27T08:12:10Z","path":"app/auth/middleware.py"}
{"type":"file.write","ts":"2026-04-27T08:13:22Z","path":"app/auth/api_keys.py"}
{"type":"command.run","ts":"2026-04-27T08:14:00Z","command":"pytest tests/test_api_keys.py","exit_code":0}
```

## 7.3 Tour

A **Tour** is the human-readable walkthrough generated from the replay.

It is ordered by comprehension, not by file path.

Example tour order:

```text
1. New concept introduced
2. Runtime entry point changed
3. Supporting helper added
4. Tests added
5. Risky/off-plan changes
6. Human review checklist
```

## 7.4 Tour step

A **Tour Step** points to specific hunks, files, evidence, and review questions.

## 7.5 Agent skill

An **openReplay skill** teaches agents to create replay artifacts after meaningful code changes.

It should work as:

```text
Claude Code skill
Open standard SKILL.md skill
Project-local skill
Global skill
```

# 9. Packaging requirements

## 9.1 Single binary

The user should install one artifact:

```bash
openreplay
```

The Go binary should embed:

```text
nvim Lua plugin
agent skill files
JSON schemas
default templates
example replay
```

Go's `embed` package supports embedding files and directories into the compiled binary.

---

## 9.2 Embedded nvim plugin

The binary should install the Lua plugin into nvim's package path.

Recommended command:

```bash
openreplay nvim install
```

Default install target:

```text
~/.local/share/nvim/site/pack/openreplay/start/openreplay.nvim/
  plugin/openreplay.lua
  lua/openreplay/init.lua
  lua/openreplay/client.lua
  lua/openreplay/tour.lua
  lua/openreplay/picker.lua
  lua/openreplay/highlight.lua
```

Neovim scans `pack/*/start/*` package directories on startup, so this works without requiring a separate plugin manager.

The Lua plugin should be thin:

```text
Lua = UI, keymaps, buffers, highlights, picker
Go = replay engine, git, schemas, tour generation, skill install
```

Neovim can communicate with external processes through jobs/channels, including `jobstart()`, `chansend()`, `rpcnotify()`, and `rpcrequest()`, so the plugin can call the Go binary over stdio or a local socket.

---

## 9.3 Embedded agent skill

The binary should install the openReplay skill in two formats:

```text
Claude Code-compatible skill
Open standard SKILL.md skill
```

Potential commands:

```bash
openreplay skill install --target claude-code --scope global
openreplay skill install --target claude-code --scope project

openreplay skill install --target standard --scope global
openreplay skill install --target standard --scope project
```

Aliases:

```bash
openreplay skill install --claude --global
openreplay skill install --claude --project

openreplay skill install --standard --global
openreplay skill install --standard --project
```

The installer should support dry-run:

```bash
openreplay skill install --claude --project --dry-run
```

And doctor:

```bash
openreplay skill doctor
```

# 10. Directory structure

## 10.1 Project-local replay directory

Default:

```text
.openreplay/
  index.jsonl
  runs/
    run_20260427_081201_bd42/
      manifest.json
      events.jsonl
      tour.jsonl
      hunks.jsonl
      evidence.jsonl
      review.jsonl
      patches/
        full.patch
        step_001.patch
        step_002.patch
      test-output/
        pytest.txt
```

## 10.2 Why JSONL?

JSONL should be the core format because:

* Events are append-only.
* Agents can write incrementally.
* Large replays can be streamed.
* It works well with CLIs.
* It is easy to debug with normal tools.
* It avoids constantly rewriting a giant JSON document.

Human-readable summary files can still exist, but canonical machine state should be JSONL.

# 11. File format

## 11.1 `manifest.json`

```json
{
  "schema_version": "0.1",
  "run_id": "run_20260427_081201_bd42",
  "title": "Add tenant-scoped API keys",
  "status": "ready",
  "created_at": "2026-04-27T08:12:01Z",
  "updated_at": "2026-04-27T08:20:33Z",
  "repo": {
    "root": "/Users/you/code/app",
    "remote": "git@github.com:org/app.git",
    "base_commit": "abc123",
    "head_commit": "def456",
    "dirty_at_start": false,
    "dirty_at_finish": false
  },
  "task": {
    "source": "beads",
    "id": "BD-42",
    "title": "Add tenant-scoped API keys"
  },
  "harness": {
    "name": "claude-code",
    "session_id": null
  },
  "artifacts": {
    "events": "events.jsonl",
    "tour": "tour.jsonl",
    "hunks": "hunks.jsonl",
    "evidence": "evidence.jsonl",
    "patch_full": "patches/full.patch"
  }
}
```

---

## 11.2 `events.jsonl`

Canonical event stream.

Example:

```jsonl
{"type":"run.started","ts":"2026-04-27T08:12:01Z","run_id":"run_abc","title":"Add tenant-scoped API keys"}
{"type":"plan.loaded","ts":"2026-04-27T08:12:02Z","source":"beads","id":"BD-42"}
{"type":"file.read","ts":"2026-04-27T08:12:10Z","path":"app/auth/middleware.py"}
{"type":"file.write","ts":"2026-04-27T08:13:22Z","path":"app/auth/api_keys.py"}
{"type":"test.run","ts":"2026-04-27T08:14:00Z","command":"pytest tests/test_api_keys.py","exit_code":0,"output_ref":"test-output/pytest.txt"}
{"type":"run.finished","ts":"2026-04-27T08:20:33Z","status":"ready"}
```

---

## 11.3 `tour.jsonl`

Each line is one tour step.

```jsonl
{"type":"tour.step","step_id":"step_001","order":1,"title":"New tenant API key model","kind":"data_model","summary":"Adds a model for hashed API keys scoped to tenants.","why":"Machine clients need tenant-scoped auth without user JWTs.","risk":"medium","files":[{"path":"app/models/tenant_api_key.py","line_start":1,"line_end":84}],"patch_ref":"patches/step_001.patch","review_questions":["Are keys stored hashed?","Can keys be revoked?"],"evidence_refs":["ev_001","ev_002"]}
{"type":"tour.step","step_id":"step_002","order":2,"title":"Auth middleware now checks API keys","kind":"behavior_change","summary":"Middleware checks X-API-Key before JWT fallback.","why":"API clients need non-user authentication.","risk":"high","files":[{"path":"app/auth/middleware.py","line_start":40,"line_end":77}],"patch_ref":"patches/step_002.patch","review_questions":["Can this bypass tenant permissions?","Is JWT fallback preserved?"],"evidence_refs":["ev_003","ev_004"]}
```

---

## 11.4 `hunks.jsonl`

```jsonl
{"hunk_id":"hunk_001","step_id":"step_002","file":"app/auth/middleware.py","old_start":38,"old_lines":12,"new_start":40,"new_lines":37,"symbol":"authenticate","patch_ref":"patches/step_002.patch"}
```

---

## 11.5 `evidence.jsonl`

```jsonl
{"evidence_id":"ev_001","kind":"git_diff","summary":"TenantApiKey model added","file":"app/models/tenant_api_key.py"}
{"evidence_id":"ev_002","kind":"migration","summary":"Migration creates tenant_api_keys table","file":"migrations/0042_tenant_api_keys.py"}
{"evidence_id":"ev_003","kind":"test","summary":"API key tests pass","command":"pytest tests/test_api_keys.py","exit_code":0}
```

---

## 11.6 `review.jsonl`

User-local review state.

```jsonl
{"type":"review.step_understood","ts":"2026-04-27T09:00:01Z","step_id":"step_001","user":"local"}
{"type":"review.needs_attention","ts":"2026-04-27T09:01:22Z","step_id":"step_002","note":"Need to verify route permission behavior"}
{"type":"review.accepted","ts":"2026-04-27T09:10:11Z","run_id":"run_abc"}
```

---

## 12.2 Replay creation

Post-hoc replay from current diff:

```bash
openreplay create \
  --title "Add tenant-scoped API keys" \
  --from-diff main...HEAD \
  --plan ./plans/api-keys.md
```

From last commit:

```bash
openreplay create --from-commit HEAD
```

From staged changes:

```bash
openreplay create --from-staged
```

From working tree:

```bash
openreplay create --from-worktree
```

Finalize after agent work:

```bash
openreplay finalize
```

---

## 12.3 Agent-friendly commands

Agents need simple commands.

```bash
openreplay start --title "Add tenant-scoped API keys" --task BD-42
openreplay event file.read --path app/auth/middleware.py
openreplay event file.write --path app/auth/api_keys.py
openreplay event test.run --command "pytest tests/test_api_keys.py" --exit-code 0 --output test-output/pytest.txt
openreplay finalize --auto-tour
```

Alternative compact form:

```bash
openreplay record file.read app/auth/middleware.py
openreplay record file.write app/auth/api_keys.py
openreplay record test.run -- pytest tests/test_api_keys.py
```

# 13. Agent skill spec

## 13.1 Skill name

```yaml
name: openreplay
description: Create an openReplay artifact after code changes so the human can replay what changed, why it changed, and which hunks need review.
```

Anthropic's public skill repo notes that `name` and `description` are required frontmatter fields in `SKILL.md`.

---

## 13.2 Skill behavior

The skill should instruct agents:

1. Use openReplay when making meaningful code changes.
2. Start a replay before editing when possible.
3. Record important file reads/writes and test runs.
4. At the end, generate a tour ordered by human comprehension.
5. Do not store hidden chain-of-thought.
6. Store rationale, evidence, review questions, and exact code references.
7. Prefer JSONL event output.
8. Always include git base/head metadata.
9. Always include patches for durability.
10. Keep explanations terse and grounded in code.

# 15. Commit and git model

## 15.1 Required metadata

Every replay should include:

```text
base commit
head commit if available
dirty state
patch file
hunk references
```

## 15.2 Do not require one commit per tour step

Tour steps are comprehension units.

Commits are persistence units.

They are related but not the same.

A single commit can contain multiple tour steps. A tour step can map to multiple hunks or commits.

## 15.3 Recommended flow

For v1:

```text
base commit
agent changes
openReplay captures full.patch
tour steps point to hunks
optional final commit
```

For v2:

```text
base commit
checkpoint commits during agent run
final accepted commit may be squashed
openReplay stores patches and checkpoint refs
```

## 15.4 Replay durability rule

A replay should remain useful even if:

* The branch is later squashed.
* The original worktree is deleted.
* The repo has moved forward.
* The line numbers drift.

Therefore, always store:

```text
git refs when available
patches always
hunk context always
symbol names when possible
```

# 17. Security and privacy

openReplay may capture sensitive data.

Rules:

1. Do not capture secrets by default.
2. Redact likely secrets in tool outputs.
3. Do not store hidden chain-of-thought.
4. Avoid committing `.openreplay/` by default.
5. Add `.openreplay/` to `.gitignore` unless user opts in.
6. Provide `openreplay scrub`.
7. Provide `openreplay export` for explicit sharing.

Skills and plugins are powerful extension mechanisms and should be installed only from trusted sources.

# 23. Success metrics

## Developer value metrics

* Time to understand agent change decreases.
* Number of files manually reread decreases.
* Review confidence increases.
* Agent-generated changes are accepted more often.
* Fewer "what happened?" moments after long agent runs.

## Product metrics

* `clankstamp create` succeeds on real diffs.
* nvim replay navigation feels faster than reading a PR diff.
* Agents can reliably generate valid stamp artifacts from the skill.
* Stamps remain useful after code moves forward.

# 24. Positioning

## One-liner

**clankstamp is a standard replay format and nvim cockpit for understanding AI-generated code changes.**

## Slightly longer

**clankstamp turns agent code changes into guided replay tours, combining diffs, rationale, hunks, tests, and review questions so humans can rebuild their mental model quickly.**

## Best tagline

> Diffs show what changed. Chat says why. clankstamp lets you replay both.

# 25. Core design principles

1. **Comprehension over chronology** — Tour steps are ordered by how a human should understand the change.
2. **Evidence over self-reporting** — Every explanation should point to files, hunks, tests, or git evidence.
3. **Portable over harness-specific** — Pi, Claude Code, OpenCode, Codex, and custom agents should all be able to emit the format.
4. **Local-first** — `.clankstamp/` lives in the repo by default.
5. **One binary** — CLI, nvim plugin installer, skill installer, schemas, and templates ship together.
6. **No hidden reasoning capture** — Store concise rationale, not private chain-of-thought.
7. **Patch durability** — Replays should survive branch squashing and repo drift.
8. **nvim is the cockpit** — Go does the engine work. Lua does the UI.

# 26. Open questions

1. Should the binary name be `clankstamp` or shorter alias `cs`?
2. Should `.clankstamp/` be gitignored automatically on `init`? (Default in this scaffold: yes.)
3. Should project-local skills install under `.agent-skills/`, `.claude/skills/`, or both?
4. Should the v1 nvim plugin require a running daemon, or shell out per command?
5. Should tour generation be purely local using the current harness, or should the agent skill own generation?
6. Should `clankstamp create --auto-tour` call an external model, or just scaffold a stamp and let the agent fill it?
7. Should patches be stored as full unified diffs only, or also split by step?
